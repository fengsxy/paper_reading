## 1. Task

**问题形式化**：

大多数 Agent 系统要么（a）用自然语言做推理，要么（b）用僵硬的规划形式化方法。两者都有局限：自然语言推理难以验证，形式化方法难以处理开放域的复杂性。

**目标**：让 Agent 构建并维护一个**可执行的 Python 世界模型**——把对环境的理解写成代码，通过运行代码来验证预测，在采取行动前先在模拟环境中规划。

## 2. Challenge

| 方法 | 困境 |
|------|------|
| 自然语言推理 | 难以捕捉矛盾，无法验证 |
| 形式化规划 | 难以处理开放域，需要人工设计 formalism |
| 传统世界模型 | 只描述，不验证，难以与真实环境交互 |

**根本问题**：世界模型如果只是"描述性的"，就无法捕捉自己的错误——需要一个**可验证的、可执行的**世界模型。

## 3. Insight & Novelty

### 3.1 Insight

**核心洞察**：把世界模型当成**可测试的代码**来维护。

> 关键思想：如果你能把"你对环境的假设"写成 Python 代码，你就可以运行这些代码，把预测结果和实际观察对比。
>
> 这就像科学方法：你提出假设（代码），设计实验（运行代码），观察结果（对比预测 vs 实际）。
>
> 发现矛盾时，重构代码使其更简单——这被用作 MDL（最小描述长度）简化偏好的实用替代。

**关键机制**：
- Agent 维护一个可执行的 Python 世界模型
- 用先前的观察验证模型预测
- 通过重构使模型趋向更简单的抽象
- 在模型中模拟规划，然后才在真实环境中执行

### 3.2 Novelty

**创新点 1**：世界模型即代码
- **解决的问题**：如何让世界模型可验证
- **受启发于**：科学方法 → 假设-实验-验证
- **具体设计**：把环境假设写成 Python 函数，输入观察，输出预测，可直接运行

**创新点 2**：MDL 简化偏好的实用替代
- **解决的问题**：计算真正的 MDL 不可行
- **受启发于**：代码重构 = 简化抽象
- **具体设计**：定期重构世界模型使其更简单，作为泛化能力的代理指标

**创新点 3**：在模拟中规划
- **解决的问题**：真实环境中的行动不可逆
- **受启发于**：模拟 before 真实执行
- **具体设计**：在可执行模型中模拟多种行动路径，选择最优后在真实环境执行

## 4. Potential Flaw

### 4.1 情境局限

- **只在 ARC-AGI-3 上验证**：抽象推理语料，泛化到开放域真实任务的效果未知
- **代码能力的依赖**：要求 LLM 有较强的 Python 编码能力
- **模型维护开销**：随着任务复杂度增加，世界模型本身可能变得复杂难以维护

### 4.2 数据问题

- **世界模型的初始构建**：如何从少量观察中构建准确的初始模型
- **模拟与真实的 gap**：模拟环境可能无法完全反映真实环境的复杂性

### 4.3 值得深挖的方向

**最值得做的问题**：这个框架是否可以与 dLLM 结合？

> dLLM 的去噪过程本身就可以看作一个"可执行的世界模型"——每个去噪步骤都在根据当前状态预测下一个状态。
>
> 如果把 dLLM 的去噪轨迹理解为一个"可执行的模拟"，那么 VSB 的 self-containedness 判断就是在问：这个模拟是否已经收敛到可信的状态？
>
> 这个类比可能开辟一个新的研究方向：把 dLLM 作为可执行的生成式世界模拟器。

## 5. Motivation

**General idea 推导路径**（第一性原理）：

> 我们为什么相信一个 Agent 对环境的理解是对的？
>
> 答案不能只是"它说得很有道理"——这无法捕捉自相矛盾。
>
> 科学方法给我们的启发是：把你的假设明确写出来，然后用它做预测，最后把预测和现实对比。
>
> 如果你不能把你的假设写成可执行的东西，你就无法真正验证它。
>
> 这就是 Executable World Model 的核心洞察：**把隐性的环境假设变成显性的、可执行的代码，然后运行它来验证**。
>
> 代码的好处是：它可以被执行，可以被测试，可以被重构。而自然语言的描述无法做到这一点。
