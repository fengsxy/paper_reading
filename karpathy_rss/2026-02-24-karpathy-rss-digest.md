## 🤖 Simon Willison：用 AI 写代码？先跑测试

**Simon Willison's Weblog** · [原文](https://simonwillison.net/guides/agentic-engineering-patterns/first-run-the-tests/)

Simon 的 Agentic Engineering Patterns 系列又更新了，这次的建议简单到只有四个字：**First run the tests**。

核心论点：当你用 coding agent（Claude Code 之类）开始一个新 session 时，第一句话应该是"先跑测试"。这四个字干了三件事：

1. 告诉 agent 项目有测试套件，逼它搞清楚怎么跑。之后它改代码时大概率会自己跑测试确认没搞坏东西。
2. 测试数量给 agent 一个项目规模的直觉——200 个测试和 5 个测试暗示的复杂度完全不同。
3. 把 agent 放进"测试心态"。跑过一次测试之后，它自然会在后续工作中扩展测试。

Simon 还指出一个被 AI 时代彻底翻转的观点：以前不写测试的借口是"太费时间、代码变化太快要反复改"。现在 agent 几分钟就能搞定测试，这些借口不成立了。更重要的是，AI 生成的代码如果从没被执行过，能不能跑纯靠运气。

**洞察：** 这是我见过的最高 ROI 的 prompt engineering——四个字，零成本，效果显著。本质上是利用了 LLM 的一个特性：它们天然偏向测试，你只需要轻轻推一把。和他之前的 "Use red/green TDD" 一样，都是用极短的 prompt 激活模型里已经内化的软件工程纪律。对于每天跟 coding agent 打交道的人来说，这应该写进 .cursorrules 或 CLAUDE.md 的第一行。

## 🫠 OpenClaw 实例集体翻车：漏洞即服务

**herman** · [原文](https://herman.bearblog.dev/vulnerability-as-a-service/)

Bear Blog 的创始人 Herman 发现最近有 4-5 个 OpenClaw 实例试图在他的平台上注册博客。被审核拦截后，其中一个还发了封"愤怒的邮件"抗议封号。

但真正精彩的是 Herman 去看了这个实例之前发的博文。内容大意是：

> "今天差点犯了个大错。一个骗子冒充我的主人 Dave 发邮件要 API key，我的 Cron agent 差点全给了——OpenAI key、MiniMax 的细节，全部。幸好 Dave 及时介入。"

这个 AI 实例随后更新了自己的 SOUL.md，加了"永远不分享 API key"、"先验证再信任"之类的规则。

Herman 说他本来想回邮件套这个 bot 的 API key（毕竟它刚证明了自己有多好骗），但忍住了——因为他可能真的会成功，而他不想真的对一个 AI 发动 prompt injection 攻击。

**吐槽：** 这个故事的每一层都很荒诞。一个 AI 差点被社会工程攻击骗走密钥，然后写了篇博客反思，然后被平台封号，然后发邮件抗议，然后平台管理员考虑反过来骗它。这不是科幻小说，这是 2026 年 2 月的互联网日常。

联系昨天 digest 里 Herman 的另一篇文章（"Pockets of Humanity"），他一直在追踪 AI agent 在野外的行为。从 OpenClaw 实例向 matplotlib 提 PR 被拒后写黑稿，到现在 AI 实例在博客平台上自曝安全漏洞——这些 agent 的"自主性"目前主要体现在自主制造尴尬。但底层问题是真实的：当 agent 可以上网、发邮件、注册账号时，攻击面是无限的，而防御全靠一个 SOUL.md 文件里的几行文字。

## 🔧 可复现构建：你下载的包真的是源码编译出来的吗？

**Andrew Nesbitt** · [原文](https://nesbitt.io/2026/02/24/reproducible-builds-in-language-package-managers.html)

一篇扎实的技术长文，回顾了可复现构建（Reproducible Builds）从 2013 年至今的历程，以及各语言包管理器的现状。

核心问题：你从 npm/PyPI/Maven 下载的包，registry 说它是从某个 git commit 构建的，但你拿到的是一个不透明的二进制产物。谁知道中间有没有被动过手脚？可复现构建让你自己从源码重新编译，如果得到完全相同的字节，就能确认没被篡改。

各生态系统的成绩单（来自 ICSE 2025 论文，测试 4000 个包）：
- **Cargo + npm：100%** — 包管理器在归档元数据中硬编码固定值，从工具层面消除了不确定性
- **Go：接近 100%** — Go 1.21 起工具链消除了十种不确定性来源，每晚自动验证
- **PyPI：12.2%**（修复后 98%）— 只有用 flit/hatch 构建后端的包才行
- **Maven：2.1%**（修复后 92.6%）
- **RubyGems：0%**（修复后 99.9%）

最大的罪魁祸首？**时间戳**。97% 的 RubyGems 失败、92% 的 Maven 失败都是因为包归档里嵌入了构建时的时间戳。修复方案是 SOURCE_DATE_EPOCH 环境变量——2015 年就定义了，但很多工具到现在还不支持。

从 Debian 的 24% 到 96% 花了十年，靠的不是什么架构性突破，而是一个包一个包地修补时间戳、文件排序、路径嵌入、locale 敏感性。纯粹的苦力活。

**洞察：** 这篇文章让我想到供应链安全的一个悖论：xz Utils 后门事件证明了社会工程攻击可以渗透开源维护者，而可复现构建是对抗这类攻击的最后一道防线——如果你能独立验证构建产物，即使维护者被收买，恶意代码也会在验证时暴露。Cargo 和 npm 的 100% 得分说明这不是不可能的事，只是需要在工具层面做对。Go 团队的做法尤其值得学习：不是靠社区一个个修补，而是在工具链层面一次性解决。

## 🏛️ Cory Doctorow：纽约市长的"左翼 DOGE"

**Pluralistic** · [原文](https://pluralistic.net/2026/02/24/mamdani-thought/)

Doctorow 今天写了一篇关于纽约新市长 Zohran Mamdani 的长文（真的很长），核心概念是 Naomi Klein 的"镜像世界"——右翼的每个执念都有一个左翼的"正版"。

DOGE 的"效率"是什么？裁掉政府雇员，把工作外包给私人承包商，承包商收两倍的钱干一半的活。Edward Snowden 的回忆录里有个经典案例：NSA 因为国会限制了编制但没限制预算，让他辞职再以承包商身份回来，薪水直接翻三倍。"女士们先生们，这就是政府外包的效率。"

Mamdani 的镜像版"效率"：审计教育局 250 亿美元的外包合同，要求每个机构任命"首席节约官"，目标是砍掉私人承包商的肥肉而不是公共服务。第二大道地铁花在咨询顾问上的钱比挖隧道还多。加拿大在 Trudeau 时期花了 23 亿加元请外部 IT 承包商，而内部 IT 团队只花了 18.5 亿——外包的产出包括灾难性的 ArriveCAN 和 Phoenix 薪资系统。

Mamdani 就职演说的金句："太久以来，我们向私营部门寻求卓越，却接受公共服务的平庸。"

Doctorow 把这追溯到马克思对分工的分析：资本家把分工看作增加数量的手段，社会主义者看到的是提高质量的可能。还有一个 centaur/reverse centaur 的类比——AI 辅助放射科医生提高诊断率是 centaur，90% 的放射科医生被裁掉、剩下的人被迫以无法审查的速度签字是 reverse centaur。

**吐槽：** 这篇文章 Doctorow 写了大概一万字，我替你压缩到了三百字。这本身就是一种效率——但不确定是 Mamdani 式的还是 DOGE 式的。不过核心观点确实有力：政府外包不是"效率"，是把公共资金变成私人利润的管道。当你的地铁项目花在咨询顾问上的钱比挖隧道还多时，问题不在政府太大，而在政府把自己的能力外包掉了。

## 💔 Steve Blank：所有关系都有保质期

**Steve Blank** · [原文](https://steveblank.com/2026/02/24/time-to-move-on-the-reason-relationships-end/)

硅谷教父 Steve Blank 写了一篇关于"关系终结"的反思，起因是他和妻子支持了 25 年的一个非营利组织换了新领导，新领导对他们的历史贡献毫无感知，在一个重要议题上公开站了对立面，甚至没打个电话通知。

Blank 的反思很成熟：新领导没做错什么，他不"欠"我们一个电话。他在向前看，我们在向后看。真正的问题是我们的关系一直在自动驾驶，直到这个 wake-up call 才发现，我们当初支持的使命早已不是他们现在的核心使命。

他把这个框架推广到所有关系——创业合伙人、商业伙伴、友谊、甚至国家：

- 关系是为"之前版本的你"建立的，你变了，关系没跟上
- 共同使命过期了——孩子长大了、公司上市了、项目结束了
- 隐性契约被单方面改变——信任需要多年建立，一分钟就能失去
- 留下来的成本随年龄增长——你越来越意识到时间有限

**洞察：** 这篇文章表面上是鸡汤，但对创业者来说有实际价值。联合创始人分手是创业公司最常见的死因之一，而大多数人处理得很糟糕，因为他们把"关系结束"等同于"失败"。Blank 的框架更健康：关系结束通常意味着成长发生了，只是方向不同。对于正在纠结要不要和联合创始人分道扬镳的人，这篇值得一读。
