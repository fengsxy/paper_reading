# Read-Copy Update：读者不付费，写者全买单

> 论文: *Read-Copy Update: Using Execution History to Solve Concurrency Problems* (McKenney & Slingwine, PDCS 1998) 及后续 *Read-Copy Update* (McKenney & Slingwine, Ottawa Linux Symposium 2001)

## 1. 背景与动机

在操作系统内核中，有一类极其常见的数据访问模式：**读多写少**。路由表、进程列表、模块列表、文件系统的 dentry 缓存——这些数据结构被频繁读取，但很少被修改。以 Linux 的路由表为例，每个网络包的转发都需要查询路由表（读操作），但路由表的更新可能每秒只发生几次。

传统的并发控制方案在这种场景下都不够理想：

- **读写锁（rwlock）**：允许多个读者并发，但每个读者仍需获取共享锁。在多核系统上，获取共享锁涉及对锁变量的原子修改（递增读者计数器），这会在所有读者的缓存之间产生一致性流量。当读者数量很大时，rwlock 的读端开销与核心数成正比——这完全违背了"读操作应该便宜"的直觉。
- **无锁数据结构**：可以避免锁的开销，但设计和验证极其困难，且通常需要复杂的内存回收机制（如 hazard pointers）。
- **顺序锁（seqlock）**：读者无锁，但需要在读取前后检查版本号，如果版本号变化则重试。对于需要跟随指针遍历数据结构的场景（如链表遍历），seqlock 不适用——因为写者可能在读者遍历过程中释放了某个节点的内存，导致读者访问已释放的内存。

Paul McKenney 和 John Slingwine 在 DYNIX/ptx 操作系统（Sequent 公司的对称多处理器 UNIX）的开发中面对了这个问题。他们的洞察是：**如果我们能保证读者在访问数据结构期间，写者不会释放任何读者可能正在访问的内存，那么读者就完全不需要任何同步操作**。

这就是 Read-Copy Update（RCU）的核心思想：读者完全无锁、无原子操作、无内存屏障；写者负责创建数据的新副本、原子地发布更新、并等待所有可能看到旧数据的读者完成后再回收旧数据。

## 2. 核心设计与关键创新

### 2.1 RCU 的三个基本操作

**读端临界区（Read-side Critical Section）**：
```
rcu_read_lock();
// 读取共享数据结构
// 可以跟随指针、遍历链表等
rcu_read_unlock();
```

在 Linux 的经典实现中，`rcu_read_lock()` 和 `rcu_read_unlock()` 仅仅是禁用和启用内核抢占（preemption），不涉及任何原子操作、内存屏障或缓存行修改。在非抢占式内核中，它们甚至可以是空操作（no-op）。这意味着读端的开销几乎为零。

**写端更新（Update）**：
写者遵循"Read-Copy-Update"三步走：
1. **Read**：读取指向旧数据结构的指针。
2. **Copy**：创建旧数据结构的副本，在副本上进行修改。
3. **Update**：使用原子的指针赋值（`rcu_assign_pointer()`）将共享指针从旧数据切换到新数据。

指针赋值是原子的（在大多数架构上，对齐的指针写入天然是原子的），因此读者要么看到完整的旧数据，要么看到完整的新数据，不会看到中间状态。

**宽限期等待与回收（Grace Period & Reclamation）**：
写者在发布新数据后，不能立即释放旧数据——因为可能还有读者正在访问旧数据。写者调用 `synchronize_rcu()` 等待一个宽限期（grace period）结束，确保所有在更新之前开始的读端临界区都已完成，然后安全地释放旧数据。

### 2.2 宽限期的定义

宽限期是 RCU 最精妙的概念。一个宽限期的结束意味着：**系统中每个 CPU 都至少经历了一次上下文切换（或处于空闲状态、或处于用户态）**。

为什么上下文切换是关键？因为 `rcu_read_lock()` 禁用了抢占，所以在 RCU 读端临界区内不会发生上下文切换。反过来说，如果一个 CPU 发生了上下文切换，就意味着它不在任何 RCU 读端临界区内。当所有 CPU 都经历了上下文切换后，就可以确定没有任何读者还在访问旧数据。

这种状态被称为**静默状态（Quiescent State）**。每个 CPU 经历一次静默状态后，宽限期结束。

### 2.3 发布-订阅机制

RCU 使用精心设计的内存屏障来保证发布-订阅语义：

- **写端**：`rcu_assign_pointer()` 在指针赋值前插入写内存屏障（write barrier），确保新数据结构的所有字段在指针发布之前对其他 CPU 可见。
- **读端**：`rcu_dereference()` 在指针读取后插入数据依赖屏障（data dependency barrier），确保通过指针访问的数据是最新的。在大多数架构（如 x86）上，数据依赖屏障是免费的（硬件保证）；在 Alpha 架构上需要显式屏障。

## 3. 重要技术细节

### 3.1 链表操作的 RCU 化

RCU 最常见的应用场景是链表操作。以删除链表节点为例：

**传统方案**（需要锁）：
1. 获取锁
2. 修改前驱节点的 next 指针，跳过待删除节点
3. 释放锁
4. 释放节点内存

**RCU 方案**：
1. 修改前驱节点的 next 指针（原子指针赋值），跳过待删除节点
2. 调用 `call_rcu()` 注册一个回调，在宽限期结束后释放节点内存

关键在于步骤 1 之后，新的读者不会再看到被删除的节点（因为链表已经绕过了它），但正在遍历链表的旧读者可能仍持有指向该节点的指针。`call_rcu()` 确保在所有旧读者完成后才释放内存。

### 3.2 宽限期的实现

Linux 内核中 RCU 的宽限期检测经历了多次演进：

- **经典 RCU**：每个 CPU 维护一个静默状态计数器。当 CPU 发生上下文切换、进入空闲状态或执行用户态代码时，递增计数器。宽限期检测器定期检查所有 CPU 的计数器，当所有计数器都递增过至少一次时，宽限期结束。
- **Tree RCU**：为了扩展到大量 CPU，使用树形结构聚合静默状态报告，避免单个全局计数器的竞争。
- **Preemptible RCU**：支持可抢占内核，读端临界区内可以被抢占。实现更复杂，需要显式跟踪哪些任务处于读端临界区内。

### 3.3 `call_rcu()` 与 `synchronize_rcu()`

RCU 提供两种等待宽限期的方式：

- **`synchronize_rcu()`**：同步等待，调用者阻塞直到宽限期结束。简单但可能导致较长的等待。
- **`call_rcu(callback, data)`**：异步回调，注册一个函数在宽限期结束后被调用。不阻塞调用者，但需要管理回调队列。

在实践中，`call_rcu()` 更常用，因为它允许写者在等待宽限期的同时继续执行其他工作。

### 3.4 RCU 的语义限制

RCU 并非万能的。它有明确的适用条件：

- **读端临界区不能睡眠**（经典 RCU）：因为 `rcu_read_lock()` 仅禁用抢占，如果读者睡眠，会无限期延长宽限期，阻塞所有等待回收的写者。SRCU（Sleepable RCU）放宽了这个限制，但代价是读端开销增加。
- **写者之间需要额外同步**：RCU 只解决读者与写者之间的同步，多个写者之间仍需使用锁或其他机制来互斥。
- **适合指针介导的数据结构**：RCU 的发布-订阅机制依赖原子的指针赋值，最适合链表、树、哈希表等通过指针链接的数据结构。

## 4. 优缺点分析

### 优点

- **读端零开销**：在非抢占式内核中，读端临界区的开销literally为零（空操作）。即使在抢占式内核中，也仅仅是修改一个 per-CPU 的抢占计数器，不涉及任何跨 CPU 的通信。
- **完美的读端可扩展性**：读端没有任何共享的可写数据，因此读者数量的增加不会产生任何额外的缓存一致性流量。这是理论上的最优解。
- **无死锁**：读端不获取任何锁，因此不可能与任何锁产生死锁。
- **读者不阻塞写者**：写者可以随时发布更新，不需要等待读者完成。
- **存在性保证**：在 RCU 读端临界区内，读者可以安全地持有指向数据结构的指针，保证该内存不会被释放。

### 缺点

- **写端开销较高**：写者需要复制数据结构、等待宽限期、管理回调队列，开销显著高于简单的锁方案。
- **内存开销**：在宽限期结束前，旧数据和新数据同时存在于内存中，增加了内存占用。在极端情况下（宽限期很长、更新频繁），内存开销可能很大。
- **宽限期延迟**：旧数据的回收不是即时的，需要等待宽限期结束。这引入了不确定的延迟，在实时系统中可能是问题。
- **编程模型的微妙性**：正确使用 RCU 需要深入理解内存模型、发布-订阅语义、宽限期的含义等概念。误用 RCU（如在读端临界区外解引用 RCU 保护的指针）会导致难以调试的 use-after-free bug。
- **不适合写密集场景**：当写操作频繁时，大量的复制和宽限期等待会成为性能瓶颈。

## 5. 历史影响与后续发展

RCU 是过去 30 年操作系统领域最成功的并发原语创新之一。

**Linux 内核的核心基础设施**：RCU 于 2002 年被合并入 Linux 2.5 内核，此后成为内核中使用最广泛的同步机制之一。截至 2020 年代，Linux 内核中有超过 10,000 处 RCU API 的使用，覆盖网络子系统（路由表、连接跟踪）、VFS（dentry 缓存、inode 查找）、安全模块（SELinux 策略查找）、设备驱动等几乎所有子系统。

**RCU 变体的演进**：
- **SRCU（Sleepable RCU）**：允许读端临界区睡眠，代价是读端需要操作 per-CPU 计数器。
- **Tree RCU**：使用层次化的树结构来扩展宽限期检测，支持数千个 CPU。
- **Expedited RCU**：通过 IPI（处理器间中断）强制所有 CPU 快速报告静默状态，缩短宽限期，但增加了系统开销。
- **Tasks RCU**：专门用于跟踪自愿上下文切换，用于 BPF 程序等场景。

**对用户态并发的影响**：RCU 的思想被移植到用户态库中，如 liburcu（userspace RCU）。用户态 RCU 的实现更具挑战性，因为用户态线程可以被任意抢占和调度，不像内核线程那样可以通过禁用抢占来界定读端临界区。liburcu 使用信号机制或内存屏障来实现类似的语义。

**对数据库系统的影响**：RCU 的"多版本共存+延迟回收"思想与数据库中的 MVCC（多版本并发控制）有深层联系。一些现代数据库（如 Silo、ERMIA）直接使用 RCU 风格的 epoch-based reclamation 来管理内存回收。

**对编程语言的影响**：Rust 的 crossbeam 库中的 epoch-based garbage collection 直接受 RCU 启发。Go 语言的某些内部数据结构也使用了类似 RCU 的技术。

**形式化验证**：RCU 的正确性验证是一个活跃的研究领域。研究者使用 CBMC、SPIN、甚至 Coq 等工具对 RCU 的各种实现进行形式化验证，发现并修复了多个微妙的 bug。这些工作也推动了弱内存模型（weak memory model）形式化的发展。

RCU 的深远意义在于它证明了一个反直觉的设计原则：**通过让写者承担更多工作，可以让读者的开销降到绝对零**。在读多写少的场景下，这种不对称的设计能带来巨大的整体性能提升。更广泛地说，RCU 展示了"延迟回收"（deferred reclamation）作为一种通用的并发编程技术的威力——不急于清理旧数据，而是等到安全时再清理，这个简单的思想解决了并发编程中最棘手的内存回收问题。
