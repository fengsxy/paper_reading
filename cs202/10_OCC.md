# 乐观并发控制：先做了再说的并发哲学

> 论文: *On Optimistic Methods for Concurrency Control* (Kung & Robinson, ACM TODS 1981)

## 1. 背景与动机

1981 年，数据库系统正处于从理论走向大规模实用的关键时期。并发控制（Concurrency Control）是数据库系统的核心问题之一：多个事务同时访问共享数据时，如何保证每个事务看到的数据是一致的，同时又不过度牺牲性能？

当时的主流方案是**悲观并发控制（Pessimistic Concurrency Control）**，其代表是两阶段锁协议（Two-Phase Locking, 2PL）。2PL 的核心思想是"先锁后做"：事务在访问任何数据项之前必须先获取相应的锁，读操作获取共享锁，写操作获取排他锁。所有锁在事务提交前不能释放（两阶段性质）。

2PL 虽然能保证可串行化（Serializability），但存在几个显著问题：

- **锁开销**：即使在没有冲突的情况下，每次数据访问都需要获取和释放锁，涉及锁管理器的查找、哈希表操作、可能的上下文切换等开销。
- **死锁风险**：多个事务互相等待对方持有的锁，导致死锁。系统需要额外的死锁检测或预防机制。
- **阻塞等待**：当一个事务持有锁时，其他需要同一数据的事务必须等待，即使最终它们之间并不存在真正的冲突。
- **对只读事务不友好**：在读多写少的工作负载中，大量只读事务仍然需要获取共享锁，产生不必要的开销。

Kung 和 Robinson 观察到一个关键事实：**在许多实际工作负载中，事务之间的冲突是罕见的**。大多数事务访问的数据集互不重叠，或者以只读方式访问。在这种情况下，悲观地为每个操作加锁是一种浪费。

基于这个观察，他们提出了一种截然不同的思路：**让事务先自由执行，不加任何锁；执行完毕后再检查是否与其他事务发生了冲突；如果没有冲突就提交，有冲突就回滚重试**。这就是乐观并发控制（Optimistic Concurrency Control, OCC）。

## 2. 核心设计与关键创新

### 2.1 三阶段执行模型

OCC 将每个事务的执行分为三个阶段：

**阶段一：读阶段（Read Phase）**

事务读取所需的数据项，但所有写操作都在本地的私有工作空间（private workspace）中进行，不直接修改数据库。事务维护两个集合：
- **Read Set (RS)**：事务读取过的所有数据项
- **Write Set (WS)**：事务打算写入的所有数据项及其新值

在这个阶段，事务完全不与其他事务交互，不获取任何锁，因此可以完全并行执行。

**阶段二：验证阶段（Validation Phase）**

事务完成所有计算后，进入验证阶段。系统检查该事务是否与其他已提交或正在验证的事务存在冲突。验证的核心问题是：如果这个事务提交，是否会违反可串行化？

**阶段三：写阶段（Write Phase）**

如果验证通过，事务将私有工作空间中的修改写入实际数据库，然后提交。如果验证失败，事务被中止（abort），所有修改被丢弃，事务可以重新开始。

### 2.2 验证条件

验证是 OCC 的核心。论文提出了三个充分条件，满足任意一个即可保证可串行化。对于事务 Ti（待验证）和所有在 Ti 之前提交的事务 Tj：

**条件一**：Tj 在 Ti 开始读阶段之前就已经完成了写阶段。这是最简单的情况——两个事务在时间上完全不重叠。

**条件二**：Tj 的写集与 Ti 的读集不相交（WS(Tj) ∩ RS(Ti) = ∅），且 Tj 在 Ti 开始写阶段之前完成了写阶段。这意味着 Ti 没有读到 Tj 写的任何数据，所以 Tj 的写入不会影响 Ti 的执行结果。

**条件三**：Tj 的写集与 Ti 的读集和写集都不相交（WS(Tj) ∩ RS(Ti) = ∅ 且 WS(Tj) ∩ WS(Ti) = ∅），且 Tj 在 Ti 完成读阶段之前完成了读阶段。这是最宽松的条件，允许两个事务的读阶段重叠。

### 2.3 串行验证与并行验证

论文提出了两种验证方案：

- **串行验证**：验证和写阶段作为一个临界区串行执行。简单但可能成为瓶颈。
- **并行验证**：允许多个事务同时进行验证和写入，但需要更复杂的条件检查（条件三）。

## 3. 重要技术细节

### 3.1 事务编号与排序

每个事务在进入验证阶段时被分配一个单调递增的事务编号（transaction number）。这个编号定义了事务的串行化顺序。注意，编号不是在事务开始时分配的，而是在验证时——这意味着事务的串行化顺序由它们的验证顺序决定，而非开始顺序。

### 3.2 私有工作空间的实现

论文讨论了两种实现私有工作空间的方法：

- **完整复制**：为每个事务创建所有待修改数据项的完整副本。空间开销大，但实现简单。
- **写时复制（Copy-on-Write）**：只在事务首次修改某数据项时才创建副本。节省空间，但需要额外的间接层。

实际系统中通常使用后者，配合版本链（version chain）来管理多个事务的私有副本。

### 3.3 只读事务的优化

OCC 对只读事务特别友好：由于只读事务没有写集，它们的验证可以大幅简化。在串行验证方案中，只读事务甚至不需要进入临界区——它们只需检查自己的读集是否与已提交事务的写集冲突即可。这使得只读事务几乎是零开销的。

### 3.4 饥饿问题

OCC 的一个潜在问题是饥饿（starvation）：一个长事务可能反复被短事务的写入所冲突，导致反复回滚。论文承认了这个问题，但认为在冲突率低的场景下，饥饿的概率很小。后续研究提出了多种缓解策略，如指数退避（exponential backoff）和优先级机制。

### 3.5 与 2PL 的理论比较

论文从理论上分析了 OCC 与 2PL 的性能权衡：

- **低冲突场景**：OCC 优于 2PL，因为省去了锁的开销。
- **高冲突场景**：2PL 可能优于 OCC，因为 OCC 的回滚代价（浪费已执行的计算）可能超过锁等待的代价。
- **临界点**：存在一个冲突率的临界点，低于该点 OCC 更优，高于该点 2PL 更优。

## 4. 优缺点分析

### 优点

- **无锁执行**：读阶段完全不需要锁，消除了锁管理开销和死锁风险。
- **读事务友好**：只读事务几乎零开销，非常适合读多写少的工作负载（如 OLAP、Web 应用）。
- **高并发度**：事务在读阶段可以完全并行，不存在阻塞等待。
- **概念简洁**：三阶段模型清晰优雅，易于理解和推理正确性。

### 缺点

- **回滚代价高**：验证失败时，事务已经完成了所有计算，回滚意味着这些计算全部浪费。对于长事务或计算密集型事务，这个代价尤其高昂。
- **高冲突场景性能差**：当冲突频繁时，大量事务被回滚重试，系统可能进入"活锁"状态，吞吐量反而低于悲观方案。
- **验证瓶颈**：串行验证方案中，验证阶段是全局串行点，可能成为性能瓶颈。并行验证虽然缓解了这个问题，但增加了实现复杂度。
- **时间戳管理**：需要维护全局单调递增的事务编号，在分布式环境中这本身就是一个挑战。

## 5. 历史影响与后续发展

Kung 和 Robinson 的这篇论文是并发控制领域的奠基性工作之一，其影响远超数据库领域。

**在数据库系统中的应用**：OCC 的思想被广泛应用于现代数据库系统。PostgreSQL 的 SSI（Serializable Snapshot Isolation）借鉴了 OCC 的验证思想；Google 的 Percolator（构建在 Bigtable 之上的事务层）使用了 OCC 风格的冲突检测；CockroachDB、TiDB 等 NewSQL 数据库也采用了 OCC 或其变体。

**MVCC 与 OCC 的融合**：多版本并发控制（MVCC）与 OCC 的结合成为现代数据库的主流方案。MVCC 为每个数据项维护多个版本，读操作总是可以找到一个一致的快照，而 OCC 的验证机制用于检测写-写冲突。这种组合兼具了两者的优点。

**在内存数据库中的复兴**：随着内存数据库（如 Silo、Hekaton）的兴起，OCC 迎来了第二春。在内存数据库中，数据访问延迟极低，锁的相对开销更加显著，而 OCC 的无锁读取优势更加突出。Silo（Tu et al., SOSP 2013）展示了精心优化的 OCC 在多核内存数据库上可以达到极高的吞吐量。

**在软件事务内存（STM）中的应用**：STM 的核心思想——让程序员用事务的方式编写并发代码，由运行时系统自动处理冲突——本质上就是 OCC 在通用编程中的推广。

**在分布式系统中的延伸**：OCC 的"先执行后验证"思想也影响了分布式系统的设计。例如，分布式版本控制系统（如 Git）的"先本地修改，push 时检测冲突"模式，以及乐观复制（optimistic replication）的思想，都与 OCC 有着深层的联系。

这篇论文的持久价值在于它揭示了一个普适的设计原则：**当冲突是例外而非常态时，为最坏情况做准备（悲观方案）不如为最好情况做优化（乐观方案）**。这个原则不仅适用于数据库，也适用于网络协议（如乐观的 TCP 拥塞控制）、分布式共识（如 speculative execution）等众多领域。
