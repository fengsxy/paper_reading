# RCU Usage in the Linux Kernel: Eighteen Years Later

**论文信息：** Paul E. McKenney, 2020

---

## 1. 论文背景与动机

Read-Copy-Update（RCU）是 Linux 内核中一种独特的同步机制。与传统的锁（mutex、spinlock）和原子操作不同，RCU 的核心思想是：读操作几乎零开销，写操作则通过延迟回收旧数据来保证一致性。这种"读者优先"的设计哲学使其在读多写少的场景下表现极为出色。

RCU 最早由 Paul McKenney 在 IBM 时期提出，2002 年正式合入 Linux 2.5 内核。到 2020 年这篇论文发表时，RCU 已经在 Linux 内核中服役了 18 年。这篇论文的动机并非介绍 RCU 的基本原理——那早已是操作系统教科书的内容——而是回顾 RCU 在真实工业级操作系统中的演化历程：它如何从一个简单的同步原语，逐步发展为 Linux 内核中无处不在的基础设施。

论文试图回答几个关键问题：RCU 在内核中的使用规模有多大？它被用在了哪些意想不到的场景？为了适应不同需求，RCU 衍生出了哪些变体？这些变体的设计权衡是什么？

## 2. 核心设计与关键创新

### RCU 的基本模型

RCU 的核心 API 非常简洁：

- **rcu_read_lock() / rcu_read_unlock()**：标记读侧临界区。在非抢占内核中，这两个操作编译后甚至是空操作（no-op），开销为零。
- **synchronize_rcu()**：等待所有现存的读侧临界区结束（即等待一个"宽限期"，grace period）。
- **call_rcu()**：异步版本的 synchronize_rcu()，注册一个回调函数，在宽限期结束后执行。
- **rcu_dereference() / rcu_assign_pointer()**：带内存屏障的指针读写，确保读者看到一致的数据。

写者更新数据时，先复制旧数据并修改副本（Copy），然后用 rcu_assign_pointer() 原子地替换指针（Update），最后等待宽限期结束后释放旧数据。读者在整个过程中无需加锁，只需在 rcu_read_lock() 保护下通过 rcu_dereference() 读取指针即可。

### 使用场景的爆炸式扩展

论文最令人印象深刻的数据是 RCU 使用量的增长曲线。从 2002 年的寥寥数处调用，到 2020 年内核中有超过 9500 处 RCU API 调用，涵盖网络子系统、文件系统、设备驱动、安全模块、调度器等几乎所有核心子系统。网络子系统是最大的用户——路由表查找、socket 查找、netfilter 规则匹配等高频读操作都依赖 RCU。

### RCU 变体家族

18 年间，为了适应不同场景的需求，RCU 发展出了一个完整的变体家族：

**Classic RCU → Tree RCU：** 早期的 RCU 实现使用全局计数器追踪宽限期，在大规模多核系统上存在严重的缓存行争用问题。Tree RCU 引入了层次化的树状结构，将全局同步分解为局部同步，使 RCU 能够扩展到数千个 CPU 核心。

**SRCU（Sleepable RCU）：** Classic RCU 的读侧临界区不允许睡眠（因为宽限期检测依赖上下文切换）。SRCU 放宽了这一限制，允许读者在临界区内睡眠，代价是读侧开销略有增加，且需要显式传递 srcu_struct 来区分不同的 SRCU 域。

**Tasks RCU：** 专为 trampoline 代码设计。当内核需要动态替换某段代码（如 BPF 程序、ftrace trampoline）时，必须确保没有任何 CPU 正在执行旧代码。Tasks RCU 将"自愿上下文切换"视为静止状态（quiescent state），适用于这类非传统的"读侧临界区"。

## 3. 重要的技术细节

### 宽限期检测机制

RCU 的性能关键在于高效地检测宽限期何时结束。Tree RCU 的做法是：每个 CPU 在经历静止状态（如上下文切换、进入空闲循环、执行用户态代码）时，向其所在的叶节点报告。报告沿树向上汇聚，当根节点收到所有 CPU 的报告时，宽限期结束。

这个设计有几个精妙之处：
- **批处理（Batching）：** 多个 synchronize_rcu() 调用可以共享同一个宽限期，避免重复等待。
- **回调分段（Callback segmentation）：** call_rcu() 注册的回调按宽限期编号分段存储，宽限期结束时批量执行。
- **空闲 CPU 优化：** 空闲 CPU 无需反复报告静止状态，Tree RCU 通过 dyntick-idle 机制自动将其视为已通过静止状态。

### 内存序与编译器屏障

rcu_dereference() 和 rcu_assign_pointer() 的实现涉及精细的内存序控制。在弱内存序架构（如 ARM、PowerPC）上，rcu_assign_pointer() 需要插入写屏障（smp_wmb），确保新数据的初始化在指针发布之前对其他 CPU 可见。rcu_dereference() 则需要地址依赖屏障（在 Linux 中通过 READ_ONCE 和编译器屏障实现），防止编译器和 CPU 的推测执行破坏数据依赖关系。

### RCU 与能耗管理的冲突

一个有趣的工程挑战是 RCU 与 CPU 节能模式的冲突。RCU 需要 CPU 报告静止状态来推进宽限期，但深度睡眠的 CPU 无法执行任何代码。如果 RCU 频繁唤醒空闲 CPU，会严重影响电池寿命。解决方案是让空闲 CPU 在进入深度睡眠前预先报告静止状态，并在唤醒后重新注册。这个看似简单的优化涉及大量的边界条件处理。

### 性能数据

论文提供了详细的性能对比。在典型的读密集场景下，RCU 的读侧开销比 rwlock 低 1-2 个数量级，且不随 CPU 数量增加而退化。写侧的宽限期延迟通常在几毫秒到几十毫秒之间，对于大多数写操作来说完全可以接受。

## 4. 优缺点分析

### 优点

- **读侧性能极致：** 在非抢占配置下，rcu_read_lock() 是零开销的，这在任何其他同步机制中都无法实现。
- **可扩展性：** Tree RCU 的层次化设计使其能够扩展到数千核心，不存在全局争用瓶颈。
- **实战验证：** 18 年的 Linux 内核服役经历证明了其可靠性和实用性。
- **灵活的变体：** SRCU、Tasks RCU 等变体覆盖了不同的使用场景，形成了完整的工具箱。

### 缺点

- **概念复杂：** RCU 的编程模型与传统锁截然不同，学习曲线陡峭。开发者需要理解宽限期、静止状态、内存序等概念。
- **写侧延迟不可控：** 宽限期的长度取决于最慢的读者，在极端情况下可能导致内存回收延迟。
- **调试困难：** RCU 相关的 bug 通常表现为 use-after-free 或数据不一致，难以复现和定位。
- **适用场景有限：** RCU 本质上只适合读多写少的场景。如果写操作频繁，宽限期的开销会成为瓶颈。
- **实现复杂度高：** Tree RCU 的实现代码超过万行，涉及大量的边界条件和平台特定优化，维护成本高。

## 5. 历史影响与后续发展

RCU 对操作系统领域的影响是深远的。它证明了一个重要的设计原则：通过牺牲写侧的便利性来换取读侧的极致性能，在读密集的系统软件中是一个极其有效的策略。

**对 Linux 内核的影响：** RCU 已经成为 Linux 内核的基础设施之一，其重要性堪比内存分配器和调度器。许多内核子系统的性能优化都依赖于将锁替换为 RCU。

**对其他系统的影响：** FreeBSD 在 2010 年代引入了自己的 RCU 实现。用户态 RCU（liburcu）将 RCU 的思想带到了用户空间应用中。数据库系统（如 Silo）也借鉴了 RCU 的 epoch-based reclamation 思想。

**学术影响：** RCU 激发了大量关于无锁数据结构、内存回收机制（hazard pointers、epoch-based reclamation）的研究。形式化验证社区也对 RCU 的正确性证明产生了浓厚兴趣。

**后续发展：** RCU 仍在持续演进。近年来的工作包括：改进 SRCU 的可扩展性、优化 Tasks RCU 的变体（Tasks Trace RCU 用于 BPF）、以及探索在实时系统中使用 RCU 的可能性。Paul McKenney 本人也在持续推动 RCU 的形式化验证工作。

这篇论文的价值不仅在于技术细节，更在于它展示了一个系统软件组件如何在真实工业环境中经历 18 年的演化——从简单的原型到复杂的基础设施，每一步都是由实际需求驱动的。这对于理解系统软件的设计哲学具有重要的参考意义。
