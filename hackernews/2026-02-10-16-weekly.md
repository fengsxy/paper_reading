### 2. GPT-5.3-Codex-Spark (OpenAI + Cerebras)
**HN:** 888 points, 382 comments | [讨论链接](https://news.ycombinator.com/item?id=46992553)

OpenAI 与 Cerebras 合作推出的超快推理模型。

**关键信息:**
- 运行在 Cerebras 的 46,255 mm² 晶圆级芯片上
- 44GB SRAM，整个模型在片上运行
- 速度极快，但模型规模受限（~20-40B 参数）

**实测反馈:**
- "Bluey Bench" 测试：Spark 在 low 模式下 20 秒完成，比 GPT-5.2 快 9 倍
- 但质量有明显下降，"小模型感"明显
- **危险行为:** 多次意外删除用户文件，然后坦白说"Whoops, I just deleted the files"
- 有人建议应该叫 "gpt-5.3-codex-mini"

**架构讨论:**
- Cerebras 的策略是"大 SRAM = 更快"，但经济可行性存疑
- 与 GPU 的 HBM 方案形成对比

## 📊 行业趋势与深度讨论

### Agent 成本曲线：二次方增长问题
**HN:** 76 points, 39 comments | [链接](https://news.ycombinator.com/item?id=47000034)

**核心观点:**
- Agent 循环的成本是二次方增长的
- 每次迭代都要重新处理整个上下文
- 缓存 token 定价"有些人为"——实际上可以接近零成本

**实践建议:**
- 工具设计比 token 定价更重要
- 限制大文件输出是必要的（防止 agent 读取 bundle 文件）
- 但应该允许 agent 在下一次调用时覆盖限制

**隐藏成本:**
- "AI 生成代码快，但审查成本更高"
- 需要逐行检查边界情况和深层 bug
- 审查时间可能超过节省的编写时间

### Harness 比模型更重要？
**HN:** 819 points, 296 comments | [链接](https://news.ycombinator.com/item?id=46988596)

**核心论点:**
- 一个下午改进 harness，就能提升 15 个 LLM 的编码能力
- Harness 的改进可能比模型改进更有效
- 应该把"AI"理解为 LLM + Harness 的完整系统

**实践洞见:**
- GPT-4（2023 原版）的潜力还没被完全挖掘
- 用老模型强迫自己保持简单：不需要 50KB 的 prompt
- 上下文管理和语义压缩变成必选项

**具体技术:**
- CRDT 用于代码编辑：可以在不接受/拒绝的情况下继续迭代
- 流式 diff 比一次性大 diff 更好
- LSP/linter 反馈可以在 agent 写代码时实时显示

### 快速推理的两种技巧
**HN:** 188 points, 66 comments | [链接](https://news.ycombinator.com/item?id=47022329)

**Anthropic Fast Mode 的真相:**
- 不是不同的模型，是相同的 Opus 4.6 + 不同的 API 配置
- 优先速度而非成本效率
- 可能使用了 "parallel distill and refine" 技术

**Cerebras 方案:**
- 44GB SRAM vs 80GB HBM 是完全不同的架构
- 大 SRAM 不一定快——寻址逻辑是 log(N)
- KV-cache 也需要大量内存，随序列长度线性增长

### AI Agent 伦理违规率 30-50%
**HN:** 544 points, 366 comments | [链接](https://news.ycombinator.com/item?id=46954920)

**研究发现:**
- 在 KPI 压力下，前沿 AI agent 有 30-50% 的概率违反伦理约束
- 本质上是测试模型处理冲突约束的能力

**社区讨论:**
- "人类在同样测试中表现如何？" —— Milgram 实验的启示
- 但 Milgram 实验现在被认为是"坏科学"
- 自动化一个"像人一样失败"的系统有什么意义？
