# Analysis: EP130 - 妙鸭不是 AI Native；从流程设计到上下文设计

## 0. 3-5 句摘要

- 张月光复盘认为：妙鸭“不是 AI native 产品”，而是“把 AI 能力发挥得非常好的互联网产品”（[35:52]-[35:57]）。
- 他给出一个关键区分：
  - “没有这代 AI 技术做不了”只是必要条件，不是充分条件（[36:05]-[36:18]）。
  - AI native 更核心的特征在于输入/输出的“开放性”，尤其在 agent 时代会进一步放大（[36:25]-[37:58]）。
- 传统互联网产品的主要工作是“面向流程”的路线/按钮/动线设计；而 AI native 的构建方法更像“面向上下文”的设计：关键变成如何为模型提供它看不见但决定结果的 context / prompt（[36:39]-[37:27], [39:23]-[41:02]）。
- 他也解释了妙鸭当年的成功路径：通过限制用户自由度与固定工程链条，换取稳定效果；但这仍是互联网式“流程控制”思维（[38:08]-[38:55]）。

## 1. 反共识/非显然观点

- “用 AI 才能做”≠ AI native：妙鸭满足“没有这代技术不成立”，但仍不足以叫 AI native（[36:05]-[36:18]）。
- AI native 团队的核心协作不再是先把 UI/流程定义完再交付实现；因为无法穷举用户指令、输出也不确定，先验流程会频繁被模型行为推翻（[39:59]-[40:22]）。
- 真正决定体验的“中间层”不是 UI，而是：
  - 你如何补全用户“看不见的上下文”；
  - 上下文在生成环节造成什么影响；
  - 最佳 context / prompt 的实践是什么（[40:46]-[41:02]）。
- “单向门（One Way Door）产品”不是创造新需求，而是给旧需求一个全方位优势的新解法；哪怕当下未全面优势，但能清晰看到未来会全面优势也值得下注（[34:54]-[35:38]）。

## 2. 可学习的点（可迁移的方法论）

- 用“必要 vs 充分”框架定义 AI native：
  - 先排除掉“只是用了 AI 的旧范式产品”；
  - 再看是否具备开放输入/开放输出，以及围绕 context 的构建方法（[36:05]-[36:18], [36:25]-[37:58], [39:23]-[41:02]）。
- 复盘妙鸭的产品工程取舍：通过限制自由度（20 张照片 + 模板 + 固定生成链路）来换取稳定与可控结果；这是一种在技术不成熟期常见且有效的“约束策略”（[38:08]-[38:55]）。
- 做 agent/开放式产品时，把“模型发挥作用的那段时间”当作需求优先级中心：先明确模型要交互几次、每次需要什么输入、什么信息会显著提升结果，再去设计承载交互的流程/界面（[41:37]-[42:20]）。
- 协作方式从“交付图纸”转为“共同做上下文实验”：产品/设计/工程需要围绕 prompt/context 形成可迭代的共同语言与验证机制（[39:59]-[41:02]）。

## 3. 提问技巧（采访方法）

- 以“你今天会怎么看 X？”做复盘型开场，引导受访者给出明确结论，再展开定义与论证（[35:40]-[36:18]）。
- 用“定义对齐”推进深层认知：先抛出大众定义（AI native 的常见口径），再让嘉宾指出不足并提出自己的判准（[36:01]-[36:29]）。
- 追问“为什么协作会失效/关键在哪里”，把讨论从抽象概念落到可操作的组织与流程变化（[39:59]-[41:02]）。

## 4. 可进一步验证/挖坑

- 如果 AI native 的核心是“上下文设计”，那么：
  - context 的可复用单元是什么（数据/工具/记忆/世界模型/工作流片段）？
  - 团队如何沉淀“最佳 context”的可测试资产（[40:46]-[41:02]）？
- 妙鸭式“限制自由度换稳定”的策略在 agent 时代是否依然有效？应如何权衡开放性与可控性（[37:49]-[38:55]）？
- “单向门”判断的可验证标准是什么：如何用实验或指标证明它未来会成为“全方位优势解法”（[35:04]-[35:38]）？
